# CI/CD после v75 — выпуск без повторной сборки

## Контракт качества

- В `validate-pwa.yml` job `build` один раз собирает `dev/dist`, запускает `check-deps`, `check-bundle`, табличный тест E3 и создаёт `ci-manifest.json` с SHA-256 **каждого** файла результата.
- Jobs `golden`, `ui`, `three-d` скачивают **только этот** артефакт и проверяют манифест до тестов. Golden: обе сборки, 200 боёв, meta, saves, screens. UI: E3 на 844×390 и 667×375, замеры DOM. 3D: телефон, два цикла, одна WebGL-сессия, отсутствие роста ресурсов/ошибок.
- Job `gate` строго требует успеха всех jobs. В нём выполняется «сухая» выкладка (stage) с проверкой SHA-256 скопированных файлов. При FAIL или skipped хотя бы одного обязательного job статус FAIL; публикация запрещена.
- Эталоны переписываются **только отдельно по согласованию**. `--update` отсутствует в обычном workflow.

## Публикация

`publish-pwa.yml` запускается **только** после успешного push-validation `main` с commit message, начинающимся `release:`. Ручной запуск в обход проверок убран. Версия в `dev/version.json` определяется релизом, сами CI-правки не меняют её.

1. Checkout `main`; проверить, что HEAD равен SHA проверенного коммита.
2. По ID успешного validation-run скачать `dune-validated-build` из GitHub Actions.
3. Проверить полные SHA-256, версию в footer и версию service worker; скопировать в корень **точно проверенные** `index.html`, `app.js`, `app.css`, `sw.js`, `babylon3d.js`, `assets/`.
4. Сделать `deploy:` commit через `GITHUB_TOKEN`; отправить **один** запрос GitHub Pages rebuild. Сборка игры повторно не выполняется.
5. Сохранить метаданные в GitHub Actions job summary. Проверить итог Pages deployment; если нет успеха, релиз не считать опубликованным.

Старую открытую PR-ветку нельзя сливать, если её status checks не зелёные. GitHub Pages может сам создать отдельный сборочный run при обновлении `main`; запрос после `GITHUB_TOKEN` нужен для гарантии обновления, так как push бота сам по себе не запускает Pages. Оптимизация гарантирует один **явный** запрос, а не отсутствие любого лишнего автоматического run платформы.

## Как проверять скорость

Использовать timestamps в Actions jobs, отдельно фиксировать: push `release:` → validation success → deployment commit → Pages deploy success. Сравнить с выпуском v75. Очередь GitHub и работа Pages вне нашего контроля; целевые 5–8 минут — оценка, не SLA. Если после изменений `gate` FAIL, не обходить его ручным запуском публикации — сначала исправить проблему.

## Имена и назначения

- `dev/tools/ci-artifact.mjs make`: создаёт проверяемый манифест.
- `dev/tools/ci-artifact.mjs verify`: сверяет полный набор файлов и SHA-256.
- `dev/tools/ci-artifact.mjs stage`: сверяет артефакт и копирует тестированный билд без изменения исходников.
