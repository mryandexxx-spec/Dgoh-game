# Инструкция проекта (для любого ИИ-ассистента)

Перенесена из настроек проекта claude.ai «Дюна-Вайбклод» (09.11.2026) и адаптирована под работу только с репозиторием. При расхождении главнее `dev/ARCHITECTURE.md`.

Проект: игра «Dune: Galaxy of Houses» / «Дюна: Герои великих домов» (в стиле SWGOH, вселенная Дюны). Целевая платформа — iPhone (PWA, Safari, только альбомная ориентация); desktop вторичен.

## Источники
- Источник правды — репозиторий GitHub `mryandexxx-spec/Dgoh-game`: `dev/src` (ES-модули), `dev/tools`, `dev/tests`, `dev/assets`. Корень репозитория — собранная PWA (GitHub Pages).
- Начало работы: склонировать репозиторий (можно shallow), `cd dev && npm i`. Затем прочитать `dev/ARCHITECTURE.md` — правила архитектуры, профилей графики, производительности, процесса и ведения журнала; они обязательны для любой доработки. Команды и тесты — `dev/README.md`.
- Перед началом доработки прочитать раздел «Открыто» в `dev/CHANGES_STATUS.md` и учесть его в проекте: связанные открытые вопросы и непроверенные на iPhone пункты.
- План релиза — `dev/docs/RELEASE_BRIEF.md`; UI-кит для макетов — `dev/docs/ui_kit.html`; исторические документы — `dev/docs/` (см. `dev/docs/README.md`). Скрипты моделей (Python/Blender) — `dev/models/`.
- Не читать целиком `dev/tests/golden/data/*.b64` (это сжатые эталоны) и собранные `app.js`/`babylon3d.js`.

## Обязательно при любой доработке (кратко; детали — ARCHITECTURE.md)
- Модульность: слои `data ← logic ← ui`, `data ← render3d`; в `logic/` и `data/` нет DOM, HTML, Babylon; HTML только в `ui/`; `logic → ui` только через хуки. `src/` правится вручную, `modularize.mjs` не запускать, перенос объявлений — `tools/move-decl.mjs`, порядок модулей — цепочка импортов предшественника (`import './prev.js'; // порядок исполнения`) + `tools/split.config.mjs`. Проверки: `node tools/check-deps.mjs`, `node tools/check-bundle.mjs dist/pwa/app.js`.
- 3D: один Engine через EngineHost, сцены по контракту GameScene с `mode()`, dispose всего созданного, 0 компиляций после wake, ассеты — файлами (KTX2), не base64.
- Профили графики: все параметры качества — только в `render3d/quality.js`; каждый новый эффект задаёт поведение для HIGH / MED (телефон по умолчанию) / LOW; автопонижение и переключатель «Графика» не обходить.
- Производительность iPhone: не хуже базы последней выкатки (бюджеты — ARCHITECTURE.md §4); рост > 10% — на согласование. DOM: 0 layout в простое, анимации только transform/opacity, точечные апдейты HUD.
- Сохранения: изменение схемы — только с миграцией и проверкой golden saves.

## Проектирование и согласование

Если нет — описать проект текстом и запросить согласование.
- Новые функции и механики: спросить, хочет ли владелец участвовать. Если да — интерактивные вопросы о сути; если нет — проект на согласование. В проекте указывать затрагиваемые модули/слои, данные и миграции, влияние на производительность и профили графики, связанные пункты «Открыто».
- Любая визуальная разработка (в т. ч. модели) — статический макет на согласование до реализации (HTML на основе `dev/docs/ui_kit.html`, фейковые данные, кадры 844×390 и 667×375); заметные изменения рендера — A/B-скриншоты до/после (минимум MED `--phone` и LOW, `tests/smoke/ab.mjs`).
- Всегда критиковать предложения владельца (баланс, сложность, интерес, производительность iPhone, профили, архитектура), предлагать улучшения, ждать ответа и только потом брать в работу.

## Проверки и выкатка
- CI-сценарии и подтверждённое переиспользование результатов — `ci/STAGE3_MINIMAL_SCENARIOS_AND_PROMOTION.md`; текущие input keys и покрытие обязательны. Нет доказательства — выполнять проверки текущего diff.
- Сборка: `node tools/build.mjs --deploy` (`dist/artifact.html` + файлы по `dist/artifact-files.json`; PWA — в корень репозитория).
- Между шагами: check-deps, check-bundle, `node tests/run.mjs dist/pwa/index.html --no-dom`. Перед выкаткой: golden на обеих сборках (`npm test`); render3d — `tests/smoke/3d.mjs --cycles 3 --resource-strict` (desktop и `--phone`: один прогрев + два измеряемых цикла); DOM/CSS — `tests/smoke/dom.mjs` (desktop и `--phone`); новая статика/SW — `tests/smoke/sw.mjs`. Эталоны (`--update`) — только при осознанном изменении и только после согласия владельца; до согласия работа держится в отдельной ветке.
- Каждая доработка: номер в `dev/version.json` +1 (выводится в футере), коммит и push в `main`. (В Claude дополнительно публиковался `dist/artifact.html` в артефакт claude.ai — вне Claude этот шаг пропускается; основная поставка — GitHub Pages из корня.)
- Журнал `dev/CHANGES_STATUS.md` — единственное место записи функциональных доработок (`PHASE*_STATUS.md` — только фазы рефакторинга). Каждая выкатка в том же коммите: новая запись «### vNN — что (дата)» (сделано · замеры · проверки · что проверить на iPhone) и актуализация раздела «Открыто»: добавить новые пункты, подтверждённые владельцем перенести в «Закрыто» с версией и датой, неактуальные убрать. Если владелец сообщает результат проверки на iPhone — обновить журнал ближайшим коммитом. Записи старше ~10 версий сворачивать в краткую сводку.
- После выкатки пакета брифа — отметить статус в таблице `dev/docs/RELEASE_BRIEF.md`.
- После коммита сообщить номер версии в футере и короткий список проверок на iPhone.

## Экономия
- Проверять минимально (синтаксис, нужные тесты, 1–2 скриншота), большие файлы не читать целиком, 3D-модели и рендеры — только по прямой просьбе, тяжёлые запросы — предупреждать заранее.
- Отвечать по-русски, кратко и по делу.
