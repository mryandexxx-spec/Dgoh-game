# CI, этап 2 — выбор проверок, единый Arena review и корректный resource gate

Кандидат в PR #70. База этапа: `89715b61c032fbe707a188ad8cdae8e05c8b685c`; main остаётся v112.

## Что меняется

1. `Select required checks` читает действительный diff GitHub event. Для pull_request сравниваются base SHA и проверяемый merge SHA, для push — before и проверяемый SHA. Недоступный base, первый push, неизвестное событие, пустой diff и ручной workflow_dispatch выбирают полный CI. Нужный base при shallow checkout скачивается отдельно по точному SHA; полная история репозитория не требуется.
2. Только положительно распознанные документы пропускают сборку и браузеры: README, ARCHITECTURE, CHANGES_STATUS, документы/макеты/изображения в dev/docs и конкретный файл исходных замеров аудита. Код в docs, неизвестный путь или смесь документации с кодом запускают полный набор. Переименования проверяются как удаление плюс добавление, поэтому перенос между docs и runtime не обходится сокращённым CI.
3. Gate всегда выполняется. Он требует успешный plan, точный набор зависимостей и ожидаемый результат каждого задания. В docs-режиме допускается только намеренный skipped; в full-режиме нужен success каждого задания, включая обе матричные A/B-проверки. Неполный plan, skipped/cancelled/failed в full или лишняя зависимость блокируют gate.
4. Документационный push в main не публикует PWA: deploy требует full-mode и успешный gate. Ручной запуск всегда полный. Для исходников, зависимостей, упаковки, SW, тестов и CI сохраняется полный набор; более тонкая выборка по слоям пока не включена из-за общих зависимостей плоского бандла.
5. Удаляется отдельный arena-framing-preview.yml. Единственная обязательная проверка framing остаётся в ui-arena. MED/LOW A/B теперь два параллельных задания основного Validate: скачивают ту же dune-validated-build и проверяют SHA-256 перед сравнением с опубликованным root. Второй build и повторный framing исключены. Кадры: dune-arena-framing-<run>, dune-arena-ab-med-<run>, dune-arena-ab-low-<run>.

## Resource gate

В предыдущем тесте два цикла давали сравнение второго цикла с самим собой. Теперь после одного прогревочного полного прохода нужны **два различных измеряемых прохода**: всего `--cycles 3`. При недостатке/невалидности данных критерий не может стать PASS. Сравниваются meshes/textures после измеряемых циклов; промежуточный рост тоже не скрывается последним снимком.

`--resource-strict` возвращает ненулевой код по ресурсоёмкости/контекстам/ошибкам консоли; измерения времени и диагностические компиляции по-прежнему не превращаются в аппаратные бюджеты iPhone. Проверка контекстов требует ровно один живой контекст, а не «не больше одного», куда ошибочно входил ноль. Workflow сохраняет JSON и текстовый лог; grep по PASS больше не является протоколом результата.

Более строгий resource gate добавляет один прогон на phone и desktop. Его нельзя выкинуть ради выигрыша времени: старое зелёное состояние не подтверждало стабильность ресурсов. Фактический новый результат и длительность фиксируются в PR после CI. Если ресурс действительно растёт после прогрева, gate должен блокировать выпуск, а причина роста исследуется отдельно от выбора проверок.

## Проверки

- Node-тесты CI-плана: docs/code/mixed/unknown, принудительный full, недоступные SHA, реальные git-коммиты, пути с пробелами, переименования в runtime и обратно.
- Gate: каждый missing/failed/cancelled/unexpected-skipped job, повреждённый plan и несогласованная A/B-селекция.
- Resource result: прогрев, стабильные циклы, рост meshes/textures, промежуточный рост, отсутствующие/NaN/Infinity данные, недостаточная выборка.
- YAML, bash синтаксис и полнота gate dependencies; Node-проверки запускаются также первым заданием GitHub CI.

## Дальше

Продвижение готового PR-artifact в публикацию без полного main Validate требует отдельного provenance-контракта (source/tree/run ID и проверка фактического merge). Текущий этап его не подменяет выбором «последнего зелёного» артефакта. После согласования PR следует проверить реальные настройки Pages source и защиты main; ранее branch protection недоступна интеграции.
