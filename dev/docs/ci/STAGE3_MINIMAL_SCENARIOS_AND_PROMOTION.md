Campaign-сценарий допускает только явно перечисленные файлы карты, её UI/CSS/пресетов. `split.config.mjs` допускается лишь при добавлении точных строк новых campaign-модулей: существующие строки, порядок и иной код должны побайтно сохраняться. Изменения shared EngineHost, материалов, геометрических утилит, assets и сборки всегда выбирают full.

Для карты не требуется повторно снимать неизменённые карточки всех героев, анимации Муад-Диба и Arena. Их заменять только сокращённым общим тестом нельзя: новый целевой lifecycle действительно создаёт, рендерит и уничтожает карты L:0 и последней главы хроник. После прогрева сравнивает два отдельных прохода, проверяет освобождение сцены, один движок/контекст и отсутствие роста meshes/textures. Проверяются MED/LOW телефоны и HIGH desktop. Полный сценарий сохраняет прежние roster/battle lifecycle phone/desktop и все hero/cinematic проверки, а также включает целевой тест карт.

## Доказательство проверок

`ci-inputs.mjs` вычисляет SHA-256 по путям, режимам и Git blob ID **всех tracked-файлов кроме разрешённых документов**. Сюда входят исходники, ассеты, опубликованный root-базис A/B/SW/perf, package lock, инструменты и тесты/CI. Незакоммиченные изменения входов отклоняются. Отдельный behavior-key исключает только `dev/version.json`; поэтому изменение версии разрешает наследовать поведенческие проверки, но требует новой сборки, golden и PWA. Ни один иной вход этим исключением не покрывается.

Manifest сборки хранит оба ключа, schema, source SHA и исходный run ID. Проверка manifest сверяет текущие входы и все SHA-256 файлов, footer/version и SW cache. Повторно собираемые байты не выдаются за исходный проверенный артефакт.

Gate после успешных требуемых заданий и rehearsal публикует `dune-validation-receipt`: repository, PR, event, workflow run/attempt, source/head SHA, input keys, пройденное/унаследованное покрытие, ID и immutable ZIP digest сборки. Receipt и build хранятся 14 дней.

Для наследования выбирается **успешный run того же PR из того же репозитория и workflow**; fork, другой PR/ветка/workflow, иной attempt, неполное покрытие, неверный digest, изменённые inputs, повреждённый или истёкший artifact не подходят. Проверяются ZIP SHA-256 receipt и сборки; при извлечении сборки запрещены выход из каталога, symlink и дубликаты путей. При отсутствии пригодного доказательства выполняются необходимые проверки текущего diff. Это не выбор «последнего зелёного» артефакта по одному имени или номеру версии.

При точном совпадении ключа повторные browser/golden проверки пропускаются намеренно, сборка скачивается и проверяется заново. При совпадении только behavior-key выполняется release-сценарий, а ранее пройденные остальные проверки наследуются. Gate проверяет точный ожидаемый результат **каждого** задания: случайные skipped/cancelled/failed остаются ошибкой. Неполный план или отсутствие подтверждённого покрытия запрещает наследование.

## После merge

Main-push ищет PR, чей `merge_commit_sha` равен фактическому checkout SHA, с base main и same-repo head. Из него допускается только успешный PR-run **точного финального head SHA**. При совпадении полного input-key main скачивает ту же сборку, проверяет ZIP/files/provenance, репетирует staging и публикует её без повторных браузерных тестов. Другой merge tree, изменившийся baseline, CI или зависимости приводят к новому сценарию проверок.

Перед публикацией повторно читается актуальный main. Публикация может перейти через новые документационные коммиты только при том же input-key; изменения игровых/тестовых/сборочных входов блокируют устаревшую публикацию. Push root остаётся обычным fast-forward: гонка после проверки не перезаписывает чужие коммиты. Main runs не отменяют активную публикацию; устаревшие PR-итерации по-прежнему отменяются.

Изменение backend CI не повышает версию игры. Действующие approval/художественная приёмка сохраняются; merge остаётся отдельным действием. Автоматические branch-based Pages builds из настроек репозитория этим workflow не управляются.

## Проверка кандидата

Node-тесты проверяют выбор всех сценариев, реальный Git diff/переименования, input keys, dirty inputs, документацию после кода и version-only наследование; отказы доказательства при fork/stale/missing/altered данных и привязку к точному merge. Отдельно проверяется строгий gate и повреждённые ZIP hashes.

В GitHub первый run должен выполнить full, создать receipt и пройти новый lifecycle. Затем отдельный документационный коммит в том же PR проверяет реальный reuse без изменения игры. Итоговые run IDs и времена записываются в PR. Promotion main проверяется фикстурами точного/неверного merge; реальный push main выполняется после согласования PR.
