## P0: два издателя и фактический механизм Pages

В `validate-pwa.yml` есть рабочий `deploy-pages`: после gate он проверяет SHA-256, переносит готовую сборку в корень, коммитит её и вызывает Actions Pages deploy. Одновременно `publish-pwa.yml` подписан на успешный Validate для main и коммиты `release:`; он снова пытается публиковать ту же сборку и отдельно запрашивает branch-based Pages rebuild.

Конфликт уже воспроизведён историей: [Publish #43504314965](https://github.com/mryandexxx-spec/Dgoh-game/actions/runs/43504314965/job/132157856847) упал на `Fail if main advanced after validation` после успешной встроенной публикации v109. Издатель сам меняет main, поэтому второй издатель ожидаемо видит другой SHA. Последние пропущенные Publish runs всё равно создают шум. Требование обходить конфликт заголовком squash-коммита без `release:` прямо записано в C4.9 handoff.

**В первом PR:** удалить отдельный `publish-pwa.yml`, оставить встроенный издатель без изменений. Ограничения на validated artifact и gate сохраняются.

**Следующий шаг:** проверить настройку Pages source в Settings и оставить один поддерживаемый маршрут, предпочтительно Actions. Динамические `pages build and deployment` запускаются и на merge source, и на коммит собранного root; первый обслуживает старую сборку и не подтверждает выпуск новой. По доступным данным конфигурация Pages не прочитана, поэтому двойную схему следует считать гипотезой для настройки, а не установленным значением Settings. Branch protection недоступна интеграции (403), список rulesets пуст; обязательность gate в защите main не подтверждена.

## P1: организация CI — первый PR

### 1. Разделить UI на четыре задания

| Задание | Сценарии |
|---|---|
| `ui` | загрузочные stall/fallback проверки, E3, memory, item DOM, обновление и offline SW |
| `ui-campaign` | жесты, Campaign 2.0, панорама лагеря |
| `ui-heroes` | Duncan Meshy, Muad-Dib card, Young Baron A/B |
| `ui-arena` | baseline/candidate formation, framing, HUD, idle DOM |

Сохраняются исходные команды, размеры кадров, профили графики, выходные каталоги и имена артефактов. Каждый job скачивает одну сборку и проверяет её manifest до тестов. Все новые задания включены в fail-closed gate. При падении одной группы можно перезапустить её, не повторяя остальные 8–10 минут UI.

### 2. Разделить lifecycle и perf

Отдельно выполняются phone lifecycle, desktop lifecycle и perf. В perf остаются четыре измерения: baseline/candidate × MED/LOW. Каждый `perf.mjs` уже возвращает `camp`, `hero`, `battle`; обе существующие проверки бюджетов читают один и тот же набор JSON. Порог роста >10% и все метрики лагеря/боя сохранены.

Удаляются только четыре повторных измерения второго набора. На шести разобранных запусках этот набор занимал 122–143 с. Это экономия runner-времени, а ускорение общего run дополнительно зависит от очередей и разбиения остальных заданий. Старые названия `perf-b1-*.json` больше не создаются; диагностический артефакт содержит четыре общих `perf-*.json`.

### 3. Отменять устаревший Arena review

В отдельном Arena workflow не было concurrency; старые SHA продолжали полностью отрабатывать. В выборке 100 runs — 36 Arena review. Например, для [#201](https://github.com/mryandexxx-spec/Dgoh-game/actions/runs/43582696000) повторный framing занял 100 с, A/B — 279 с. Добавлена отмена предыдущего run того же PR.

Повторный framing также уже есть в обязательном Validate. Полное объединение workflows оставлено следующим шагом: A/B на MED/LOW обязателен при заметных изменениях рендера, и его нельзя просто потерять при удалении отдельного workflow. Цель — один framing и один A/B на тех же validated bytes с ранней выдачей кадров.

### 4. SW-проверка инфраструктурных изменений

При неизменной игре baseline root и кандидат имеют одинаковый SW VER. Старая проверка A→B одновременно требовала наличие нового кэша и отсутствие старого с тем же именем — условие невыполнимо. Нельзя исправлять такой CI пустым bump версии игры или пропуском SW. Тест теперь при совпадении VER создаёт временную копию baseline с другой генерацией кэша; все shell/asset bytes и кандидат сохранены. Реальные разные версии по-прежнему проверяются напрямую. Так инфраструктурный PR упражняет обновление, перенос кэша и offline без фиктивного релиза. Подготовка фикстуры проверена отдельно на сохранность bytes и неизменность входов.

### 5. Ожидаемый результат

Цель первого этапа — примерно **5–7 минут** полного Validate вместо типичных **11–15 минут**, при достаточном числе свободных runners. Это предварительная оценка по длительностям старых шагов, а не обещанный результат. Число параллельных browser jobs увеличивается с 7 до 12; при ограниченной квоте часть встанет в очередь. Сравнить новую фактическую длительность и runner-минуты после CI, не уменьшать выборки кадров ради красивого результата.

Setup/npm/artifact overhead возрастёт на пять job, но старые измерения показывают npm ci 3–6 с, Chrome setup 8–12 с, скачивание/проверку сборки около 1–5 с. Эти накладные расходы значительно меньше сокращаемых последовательных цепочек. Пока нет оснований инвестировать в кэш node_modules или перенос на платные runners.

## P1: дефект полезности существующего lifecycle gate

`dev/tests/smoke/3d.mjs` при `--cycles 2` сравнивает `last.after` с `cycles[1].after`. Это один и тот же второй цикл: критерий «нет роста meshes/textures» всегда проходит. В #888 phone выводит meshes 172→244, desktop 174→246 и одновременно PASS «нет роста».

Это **не доказывает утечку**: рост может быть отложенным прогревом кэша. Но текущий зелёный критерий её не исключает. Удалять lifecycle как «бесполезно долгий» нельзя. Нужен отдельный ремонт: явный warm-up, затем минимум два сравниваемых стабильных цикла и машинный JSON-результат для resource safety. Тайминги SwiftShader и компиляции не следует без проверки превращать в обязательные пороги физического iPhone.

В оптимизационном PR критерий и число циклов не менялись; известный пробел сохраняется и зафиксирован, а не маскируется. В том же логе есть диагностические FAIL навигационных компиляций и ≤400 мс, которые текущий workflow сознательно не делает блокирующими. Итоговый отчёт должен различать диагностические отклонения и обязательные проверки.

## P2: сократить сам релизный цикл

C4.9 последовательно прошёл полный художественный Validate #884 (13:08), полный выпускной PR Validate #887 (12:55), затем полный main Validate #888 (14:47 с повторной попыткой). Только сумма этих запусков — **40:50**, без ожидания пользователя и разработки.

### Ближайшее изменение процесса

1. Определять номер версии и добавлять handoff до финального CI и художественной приёмки. Иначе поздний bump меняет footer/cache/сборку и по действующему контракту требует нового полного прогона.
2. Делать один законченный push на проверяемый шаг, а не серию API-коммитов с паузами в несколько секунд. В последние 100 runs 29 Validate отменены; это не ошибки игры, но затраты на старт и потеря понятной точки ожидания.
3. Между итерациями использовать предписанные check-deps/check-bundle/Node golden и затронутые smoke. Полный выпускной gate — на окончательном кандидате. Текущий первый PR автоматический запуск полного Validate не ограничивает.
4. Оставить один набор MED/LOW кадров и одну ссылку для художественной приёмки; из summary сразу отдавать campaign/hero/arena артефакт нужной доработки. Сейчас исторические package/BH/MD имена усложняют поиск.
5. При сбое инфраструктуры перезапускать конкретный failed job, а не весь workflow. После изменения исходников старые результаты не переиспользовать без доказательства их применимости.

### Два уровня проверки изменений

Предлагаемая классификация следующего PR:

| Тип изменения | Проверки |
|---|---|
| Только документация | проверка ссылок/формата; без WebGL и сборки |
| Механика, данные, сохранения | быстрые контракты + golden; профильные UI при изменении отображения |
| UI/CSS | golden + DOM + затронутые мобильные экраны |
| render3d, ассеты, загрузчики, общие графические настройки | lifecycle, perf, mobile WebGL, профильные герои/сцены, A/B |
| SW, упаковка, build, зависимости или CI | полный набор |
| Неизвестный путь | полный набор (fail closed) |

Классификация должна учитывать транзитивные зависимости, общие core/boot/состояние, PWA/статику и явный режим full. Нельзя выбирать тесты только по имени главы и пропускать общие регрессии. Required gate должен всегда запускаться и отличать намеренно невыбранное задание от аварийного skip. Обычный `paths-ignore` всего required workflow может оставить PR без завершающего статуса. Поэтому такая оптимизация в первый PR не включена.

### Продвигать проверенную сборку вместо повторного тестирования main

Целевой процесс: финальный release candidate → один полный Validate → принятые кадры → merge → verify/provenance → publish → короткий deployed smoke. Он уберёт ещё один полный Validate, но требует расширить нынешний manifest: source SHA/tree, run ID, версия инструментов, доверенный workflow и привязка к фактическому merge tree. Сейчас manifest содержит version/cache/hashes файлов, а не происхождение исходников.

При несовпадении исходников с проверенным кандидатом или при изменении main — новый Validate. Нельзя скачивать «последний зелёный артефакт» по имени, проверять только номер версии, использовать произвольный PR artifact из привилегированного workflow_run или убирать контроль exact bytes. Публикация должна быть сериализована; перед записью/деплоем проверить, что кандидат не устарел. Настройка защиты main и способ merge входят в этот этап.

## Повторные попытки и нестабильные проверки

В первом attempt #888 упал arena-animation: `flash-expired HUD projection drift u0`; в первом attempt #845 — memory-ix-dom: `667: selection modal`. Оба run затем успешны на повторной попытке. Это кандидаты на исследование синхронизации/состояния теста, а не доказанные флейки и не основание для безусловного retry. Разбиение UI уменьшает стоимость точечного перезапуска; следующий шаг — сохранять диагностический кадр, состояние и временную шкалу при первом падении.

## Что сохранять

- Быстрые контрактные/архитектурные тесты: почти бесплатны и рано ловят ошибки.
- Golden battles/meta/saves и обе поставки PWA/artifact: до отдельного решения о поддержке artifact.
- SW update/offline, stall/fallback, реальный WebGL и MED/LOW кадры.
- SHA-256 manifest, staging rehearsal, строгий gate и связь выпуска с проверенными bytes.
- Физическую проверку Safari: Chrome + SwiftShader не заменяет реальный iPhone.

Не стоит начинать с удаления golden, ослабления порогов или урезания анимаций/размеров кадров. Также не следует механически сокращать фиксированные sleep: в perf измеряется окно кадров, а часть остальных ожиданий обеспечивает завершение анимации. Следующий шаг для тестовых скриптов — readiness по состоянию сцены и измерение фазы ожидания; ограниченные timeout должны падать с понятной диагностикой.
