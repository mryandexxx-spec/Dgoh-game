## Риски конкретно для рекомендуемого B1 (`boot.js`)

- Первое различие по **0-based индексу 20**: прежний `data/looks.js` заменяется `data/story.js`. История и связанные данные вычисляются раньше, чем в v135.
- `render3d/base.js` по позициям переходит **25→54**; `assets/models.js` **52→71**; `data/story.js` **53→20**. `boot.js` остаётся 166. Это сильная, заранее известная смена порядка, а не эквивалентность.
- Историческая SCC 105 превращается в SCC 60 + 11 + 3, а **31 модуль большой старой SCC перестаёт принадлежать её циклическим частям**. Отдельная SCC 6 остаётся. Вполне возможны иные моменты чтения импортируемых live bindings и установки хуков.
- У моделей: `MODEL_DATA` начинается пустым; `b3Pre(loadAssets3)` должен быть зарегистрирован только раз. `loadB3()` при первом вызове снимает snapshot `B3_PRE`. Регистрация в root до `start()` должна предшествовать `renderLobby → mountCampStage → loadB3` и отложенному `bakePortraits()`.
- Ранние сайд-эффекты `onPersist(notePoll)`, `rewardHooks.unlock`, `set_figureSVG`, top-level `STORY/S0/NODES`, `WORM_IMG`, `set_S`, `start` обязаны оставаться корректными. Просто заменить один импорт нельзя.
- При тёплом PWA / Safari asset fetches, IndexedDB, `__B3`, WebAssembly/KTX2 и SW кэш меняют тайминг. Нужны отдельные реальные попытки и фолбэки.

## Ограниченное разрешение, которое необходимо запросить **отдельно до B1**

Предлагается согласовать **контролируемую миграцию только для root-варианта**, а не произвольную замену ESM snapshot. **Пока решение НЕ утверждено.** Отдельный B1 Draft PR должен до реальной правки иметь независимо зафиксированные оба полных списка: old 167 и proposed new 167, с hash и списком 62 позиций, а также доказательства и обязательный fail-closed gate для новой последовательности. Нельзя подогнать SPLIT к произвольному порядку.

Минимальный исходный замысел B1, пока **не реализован**:

1. В `data/story.js` удалить один side-effect `import '../assets/models.js'`.
2. В `assets/models.js` перенести **единственный** вызов `b3Pre(loadAssets3)`, сохранив неизменными модельные API, `MODEL_DATA`, загрузку DGM/KTX2 и retry; судьбу ставшего неиспользуемым named-импорта `b3Pre` решить отдельным виртуальным order-пробником (не удалять автоматически).
3. В `boot.js` импортировать `loadAssets3` и `b3Pre` и вызвать `b3Pre(loadAssets3)` **до любого вызова `start` или hot-ready callback**. Не вводить новый renderer/Engine, интервал или rAF.
4. В B1 virtual/isolated browser artifact выполнить instrumented boot trace с `B3_PRE` и первой `loadB3`, test TDZ, три EngineHost цикла, WebGL MED/LOW, warm/cold PWA/offline, Campaign 210, CELEB/NOTES, golden/saves/screens и 844×390/667×375. Не менять лагерь.
5. Только при завершённой, отдельно утверждённой успешной source реализации удалить запись baseline 1→0; затем (отдельно) ARCH-01D strict gate. Физическая Safari/iPhone проверка остаётся открытой.

## Решение A2

**NO-GO на выполнение B1 прямо сейчас; conditional GO на рассмотрение root-дизайна с контролируемой миграцией.** Сопоставление с A1 доказывает невозможность точного ESM-порядка в исследованных 63 in-memory вариантах, но не доказывает математической невозможности среди любых будущих трансформаций. Идентичность внешнего поведения должна быть отдельно проверена.

Доказательства: [A2 виртуальный CI #44277463897 — SUCCESS attempt 2 после точечного Arena HUD rerun, 19 checks + gate](https://github.com/mryandexxx-spec/Dgoh-game/actions/runs/44277463897). Первый diagnostic-only run #44277061081 имел ошибку resolver синтетического модуля, исправлен без правки игры; первая попытка полного CI упала на ~3px HUD drift, точечный неизменённый повтор SUCCESS. Эти проверки не являются real-source B1 test.

**Запрещено без отдельной команды:** реализация B1, merge, публикация, обновление approved order/SPLIT, golden, интерфейса или сцены лагеря, Campaign 2.0, баланса, сейвов и графических профилей.
