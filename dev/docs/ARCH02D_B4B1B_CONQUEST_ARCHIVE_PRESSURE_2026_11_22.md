## Verified code-path audit

1. Current v1 primary localStorage key: dune-goh-v1. Backup: dune-goh-v1.backup. Each non-no-op verified checkpoint serializes the *entire* v1 candidate, then writes a JSON envelope with the **previous** primary raw and a checksum to the backup key, confirms the backup, rechecks the primary, writes the candidate and verifies byte-exact readback. Backup and primary consume **separate** quota. There is no journal, fsync, or guarantee against origin eviction. Web Locks coordinate cooperating tabs, not cached pre-gate builds.
2. B4b1 appends a full but flat inactive prior Conquest run on forward local-week cq() reads. No expiry, ring buffer, second storage and no ability for an archived record to grant rewards. Growth is proportional to the number and density of previous runs; both primary and latest backup can contain many weeks.
3. Current manual transfer uses UTF-8 Base64 of the exact verified primary raw. Import refuses **both** input code length >2,000,000 characters and parsed candidate JSON length >2,000,000. Base64 can exceed the code limit *before* raw JSON does, especially with non-ASCII content. A displayed/exportable code is therefore not necessarily restorable by this release. Emergency RAM export is not a verified checkpoint.
4. localStorage quotas vary by browser, origin, device and Safari policies; no fixed universally safe number of weeks or 5 MiB guarantee is justified. An ordinary quota error staging backup keeps the prior primary; a quota error writing primary should leave its prior exact bytes intact, with the backup already staged. A write-then-throw produces **uncertain** outcome: never retry grants, blindly undo bytes, or claim the old primary is still authoritative.
5. B1 rollback-claim guard, C-B4 verified reward transactions, J1 unlocks, existing legacy v1 importer and fillSave, writer lease, RNG and regeneration remain unchanged. The existing B423 malformed non-array archive guard remains. This packet also refuses malformed *array entries* for forward rollover and rejects nested/broken archives in manually imported transfer code without deleting them from the original storage.

## Alternatives requiring owner decision before further implementation

| Approach | Pros | Costs / risks |
| --- | --- | --- |
| A. Lossless compact per-week snapshots inside v1 | Less storage and no new browser API | Needs strict round-trip migration, versioned decode, old PWA compatibility, no weaker reward ledger; one giant primary + backup still grows indefinitely |
| B. IndexedDB archive chunks + versioned manifest and two-phase verified commit | Per-week isolation, no single giant localStorage blob, fast scalable reads | Cross-store commit crash recovery, Safari eviction, export/import package, Web Lock ownership, migration complexity, old PWA compatibility; IndexedDB still not durable against user clearing site data |
| C. Explicit user-authorized offline archive file (versioned manifest, hashes, round-trip verified) and **only then** optional removal from active v1 | Can bound active storage with user-visible portable history | User may lose external file, needs restore UX, consent, whole-account integrity/claim guarantees; never auto-delete or pretend downloaded means independently backed up |
| D. Large-save file import/export (without changing data format) | Quickly removes 2M Base64 *transport* cliff; offline compatible | Does **not** remove localStorage/backup quota or unbounded history; requires bounded parser, protected writer/confirmation, browser/File API tests |

**Recommendation:** Next step D plus C as an explicit, reversible user-controlled export/restore workflow, while retaining all archived weeks in v1 until backup file is independently validated and approved. Evaluate compact encoding (A) only with byte-for-byte round-trip migration, and IndexedDB (B) only after a crash-consistent dual-store design. No silent eviction. Do not approve production release of unbounded archive on the strength of warning-only code.
