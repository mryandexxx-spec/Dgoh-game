# Dune GoH — AI workflow

Этот документ задаёт обязательный порядок работы AI-ассистента с задачами проекта «Дюна: Герои великих домов». Источник истины — актуальный `main` и утверждённые проектные документы.

## Обязательная проверка навыков перед каждой новой задачей

**Перед началом каждой новой задачи AI обязан самостоятельно определить, какие из уже имеющихся навыков (skills) применимы, и загрузить их инструкции непосредственно из актуального репозитория.** Пользователь не обязан называть навык, вставлять его содержимое или напоминать о проверке.

1. Прочитать актуальный `.agents/skills/README.md` в `main`, включая раздел **Routing**, и соотнести задачу с доступными навыками.
2. Для каждого применимого навыка прочитать **полный** `.agents/skills/<имя>/SKILL.md` из репозитория; при необходимости открыть указанные в нём локальные справочники `references/` и смежные навыки.
3. Использовать прочитанные инструкции при анализе, реализации, тестировании и ревью. При нескольких подходящих навыках сочетать их без дублирования работы.
4. Если подходящих навыков нет, продолжать по обычному процессу; **не выдумывать** навык и не требовать действий пользователя.
5. При смене предметной области в ходе задачи повторить проверку релевантности и загрузить дополнительные навыки. Не считать ранее запомненный список неизменным: актуальна версия из GitHub.

**Приоритет:** текущий код `main`, `dev/ARCHITECTURE.md`, `dev/docs/PROJECT_INSTRUCTIONS.md`, утверждённые ДК и решения пользователя имеют преимущество перед общими рекомендациями навыков. Применение навыков не разрешает менять архитектуру, безопасность сохранений, экономику, CI или визуальное направление без необходимых оснований и согласований.

## Обязательная художественная приёмка

Для любых визуальных изменений (3D, UI, портреты, иконки, окружение, анимации) AI обязан **самостоятельно оценить художественный результат, а не только числовые метрики и зелёный CI**, при получении каждого нового кандидата. Это отдельный обязательный критерий, не отменяющий техническую приёмку.

- Открыть и визуально изучить реальные изображения/рендеры кандидата, а не только отчёт, исходный код, наличие файла или AI-концепт. Для 3D — фактическая модель спереди, сзади, 3/4, крупный план лица, используемые позы; перед релизом — реальные кадры игры при целевых MED/LOW и размерах 844×390 / 667×375, сопоставимые с базой.
- Сопоставить с утверждённым макетом, Art Bible и релевантными референсами: силуэт, анатомия, узнаваемость, материалы, свет, детали, читаемость на телефоне, целостность стиля, артефакты и деформации. Для UI также иерархия, контраст, композиция, плотность и читаемость.
- Критически перечислить конкретные художественные дефекты и дать вердикт: принято / на доработку / визуально не проверено. Если результат слабый, продолжать итерации, не выпускать его на основании одних метрик.
- Если изображения невозможно получить или открыть, явно указать блокер и не объявлять художественную приёмку пройденной; сохранить доступные доказательства, дать прямые ссылки. Не подменять реальный рендер концептом и не просить владельца выполнять обычную проверку вместо AI.
- Существенное отклонение от согласованного направления требует согласования. Инженерный промежуточный эксперимент может пройти технический тест, но не является принятым игровым ассетом до художественной проверки.

## Рабочий цикл

После проверки навыков: восстановить контекст `main` и нужной ДК → выбрать минимальный безопасный объём изменений → отдельная ветка → адресные тесты → PR → обязательный CI → merge при зелёных проверках → проверить выпуск и отметить результат. Не запускать полный регресс только из-за наличия навыка.

Список доступных навыков и маршрутизация: [`.agents/skills/README.md`](../.agents/skills/README.md).
